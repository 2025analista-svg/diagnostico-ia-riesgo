SAT Core · flow diagrams

How an analysis flows

The system's full set of paths: the entry stretch, the four tracks it chooses from depending on the problem, the exit stretch with its two quality checks, the layers running beneath the whole flow, and how the pace changes with the working mode.

How to read them

Four kinds of step

analytical step mandatory gate stops and waits for the person quality check

The numbers are each step's position in the orchestrator's sequence: negative ones (−1, −0.5…) happen before the analysis begins (the entry stretch); positive ones (1, 2 … 13), during it. Decimals (11.3, 11.5…) are steps inserted between the main ones. A dash (—) marks a real step with no sequence number of its own.

The idea that organizes everything

There is no single pipeline. The flow has a fixed entry stretch (the gates, where the system hands control to the person), then one of four tracks is chosen based on the kind of problem —and that is the actual pipeline— and it ends with a fixed exit stretch holding the quality checks. The steps that may look "conditional" belong to a specific track: in any one session one track runs, not all of them.

Optional detour mid-analysis: the canvas for thinking  CVS

If three or more unresolved tensions pile up during a track (typically in the complex tracks, after questions are generated), the system can propose an interactive thinking artifact —a canvas or map the person fills in, selects from, and annotates— to resolve those tensions before continuing. It is not the final output: it's an intermediate tool that prevents premature synthesis (closing on conclusions before resolving what they depend on). The same format can reappear at the end as an output form, but its use here is to flex the analysis midway.

Quality control works on two levels

In the exit stretch there are two back-to-back, complementary checks: the SAT-Auditor reviews the structure of the analysis and, right after, ACR-T reviews the text of the output. They aren't substitutes — one looks at the reasoning, the other at how it's written.

Design note: the gates live inside the sequence

The gates (mode, plan confirmation, closing checks) aren't separate sections: they're numbered within the path, in the order they must be read. If a gate lives outside the execution path, a system in a hurry can skip it and start the analysis without passing through. Writing them into the sequence is what guarantees they're respected.

What runs beneath everything

The cross-cutting layers

The path reads like a sequence, but some things aren't steps: they accompany every step, reading and writing nonstop. They don't appear in the vertical chain because they don't happen "at one point" — they're there the whole time. The faint bars indicate that each layer spans the entire flow.

ELD · evidence memory

reads and writes at every step

It's not the "[0]" step that's opened and forgotten: it's the session's cumulative memory. Each skill reads it on entry (to avoid duplication and build on what came before) and writes on exit what it added: assumptions, hypotheses, blind spots, evidence assessed. If it's nearly empty at close, the system flags it.

Reading the person · every turn

modulates, doesn't decide

On each turn, the system silently reads seven signals —length, tone, sharpness, initiative…— and adjusts the intensity of its work within the chosen mode. Strict rule: it can modulate how much it pushes, but it never switches mode silently.

Risk and tradecraft · CRM + Tradecraft

built into every skill

Each skill carries a cognitive-risk profile it watches and a set of shared quality standards (how certainty is expressed, how evidence is cited, the quality check on every question). These aren't steps on the path: they're the quality substrate all of them share.

Language filter · everything visible, in plain words

top priority

Nothing shown carries technical names, acronyms, or internal structures: the machinery is translated into ordinary language before it appears. It's the system's absolute limit on what the person can see — above any other rule.

And a fifth, in its own section

The state machine (below) is cross-cutting too: it watches in the background for whether the session drifts, pauses, or gets lost, and steers it back. Five layers, then, running beneath the visible path.

Same flow, five tempos

How it changes with the mode

The working mode doesn't change which steps run —the track decides that— nor does it relax any gate. What changes is how often the flow stops and hands the turn back to the person as it moves down the pipeline. From "runs the whole thing, then you review" to "one question at a time."

The invariant the bars don't show

Whatever happens to the pace, the mandatory gates don't relax in any mode: the mode gate, the plan confirmation, S09-close, both quality checks, and the final SCQA run the same in "just give me the analysis" as in "challenge me." The mode governs when a turn comes up, not which checks apply. That's why going fast doesn't mean going without a net.

When something goes off-script

The state machine

The path above shows the route when all goes well. The system also has a state machine for when it doesn't: the person leaves and comes back, wanders off, or loses the thread. These are the loops back that a linear diagram doesn't show.

A session's nine states

PRE_ENTRADAOPENAWAITING_CONFIRMATIONCLOSEDEXPORTED DEVIATINGRECOVEREDPAUSEDDEGRADED

In grey, the normal route. In gold, the resilience states — the ones that kick in when the course has to be recovered.

Three situations

1 · The person leaves and returns later

OPEN→PAUSED→OPEN ·  or  CLOSED→EXPORTED→resumes in a new session

The state is preserved (PAUSED) or exported (EXPORTED) with a resume note and the last confirmed point. On return, the SESSION_RESUME branch skips the initial elicitation: it doesn't force repeating the context.

2 · Wandering and re-steering  REANCHOR

OPEN→DEVIATING→ [REANCHOR] →RECOVERED→OPEN

When it detects the thread has gone off the rails, it stops and re-anchors before continuing. It offers two ways out: resume from the last confirmed point, or discard and start clean. It communicates this in plain language, no acronyms. Integrity rule: you can't return to OPEN without passing through RECOVERED.

3 · The thread is lost entirely  last-resort net

DEVIATING→rebuild state from the messages→warn + offer to continue / restart

In the severe case (state lost, or output delivered without the closing checks), the system reconstructs the session backward from what was said, warns, and lets the person choose. It's the net that keeps a broken session from ending in an uncontrolled result.

Why it matters

These paths make the session recoverable: it can be paused, resumed, and re-steered without losing the work done. And they let the kind of problem change midway —which is common, because the real problem often reveals itself through analysis— without the system rigorously solving the wrong problem.
